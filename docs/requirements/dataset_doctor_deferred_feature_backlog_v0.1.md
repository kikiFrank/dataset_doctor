## 1. 状态定义与使用规则

| 标记 | 含义 | 能否进入当前开发任务 |
|---|---|---|
| `Deferred-Confirmed` | 用户明确表示暂缓，未来可重新讨论 | 不可以 |
| `Out-of-Scope` | 当前产品定位明确不做，非默认未来承诺 | 不可以 |
| `Future-Candidate` | 讨论中提出的增强设想，但尚未明确承诺 | 不可以 |
| `Pending-Decision` | 影响当前设计但尚未定案；不是“以后再说”的产品功能 | 必须先决策 |

当前版本的必选能力由需求文档与已确认的架构基线管理；它们**不应**同时作为延后项目出现。

## 2. 明确延后的数据集质量能力

### DD-FUT-001 跨视频重复帧与相似帧检查

- **状态：** `Deferred-Confirmed`
- **来源：** 讨论了“不同视频之间是否存在高度相似帧”；用户明确提出当前阶段不做，留待以后。
- **期望能力：** 比对不同视频产生的帧，发现重复或近似重复画面，辅助减少采集数据冗余。
- **将来可能涉及：** 帧级感知哈希、Embedding、场景/摄像头来源、时间窗口与候选审核。
- **当前边界：** 常规图片数据集的基础重复图片质量检查可保留；**不实现跨视频关联与去重工作流**。
- **再评估条件：** 视频导入、抽帧、Frame Metadata 和基础质量检查稳定运行后。

### DD-FUT-002 跨视频及数据划分泄漏专项审计

- **状态：** `Deferred-Confirmed`
- **来源：** 曾建议检查相近视频片段进入 Train / Val / Test 导致的泄漏；用户明确表示当前阶段暂不实现。
- **期望能力：** 检查不同视频、相邻片段或相同追踪目标跨训练/验证/测试划分的泄漏风险。
- **当前边界：** 保存视频 ID、帧索引、时间戳、Track ID 等来源信息作为后续分析基础，**不实现跨视频泄漏判断或自动重划分**。
- **再评估条件：** 有可追溯视频抽帧数据和可重复的训练集划分测试样本后。

## 5. 当前版本限制与后续兼容性建议

### DD-FUT-010 数据集合并的高级兼容性检查

- **当前明确要求：** 将来源数据转换为与目标相同的可支持格式后再合并；合并结果生成新版本，原始数据集不被覆盖。
- **当前不纳入：** 自动识别类别同名异义/异名同义、复杂类别本体映射、跨数据集的完整语义兼容性分析、自动清洗或自动划分策略。
- **未来建议（`Future-Candidate`）：** 类别名称/ID 映射建议、类别语义冲突提示、采样策略差异检查、审核与回滚向导。
- **重要风险：** **YOLO/COCO 等格式转换不能单独保证类 ID 和业务类别语义一致**。当前不做高级兼容分析属于已确认的范围限制，但开发文档和 UI 不得宣称“格式统一即合并语义安全”。
- **是否追加最低限度的用户确认步骤：** `Pending-Decision`，未来在合并发布流程设计时讨论，不在此文件中代替用户拍板。

## 6. 不应误列为延后的当前核心能力

下列功能已经在讨论中明确为当前产品关键方向，不能因为本文是“以后做的建议”而被移动到 Backlog：

- 视频播放、指定时间段标注、帧级人工标注、局部片段目标追踪辅助。
- Tracking Sampling 与 Dataset Sampling **独立配置**、固定间隔抽帧及训练数据集导出。
- 视频来源保存：原视频 ID、帧索引、时间戳、抽样配置和 Track 关系；每个 Image 维护元数据。
- Manual / AI Candidate / Final 标注并存、图层眼睛按钮、审核、修正和 Merge/Commit。
- Dataset Manager **只以已正式确认的 Final 标注**生成正式训练数据集。
- 图片质量、标注质量、语义质量体检；Agent 规划、Worker 执行、异常反馈、修复/复检。
- 允许用户选择合并现有数据集或创建新数据集，**均创建可追溯的新版本**。
- 受控的局部颜色修复及其历史记录；原始文件不得被直接覆盖。

## 7. 未来议题评估方法

如果将来要将上面的某个条目从 Backlog 移入当前版本，需先完成：

1. **价值判断**：该功能是否直接帮助数据集体检、人工复核或训练数据质量提高？
2. **竞品评估**：FiftyOne、CVAT、Cleanlab、CleanVision 等现有能力是否已经满足需求？
3. **数据依赖**：当前 Asset、Frame、Track、Annotation、Issue、Version 记录是否足以支撑功能？
4. **实现成本**：是否引入新模型、额外进程、跨平台依赖、许可限制、数据迁移或成本？
5. **验证条件**：需要怎样的代表性测试集、可测指标、异常用例和人工审核标准？
6. **正式批准**：用户确认后，先更新需求/架构/契约/测试，再加入开发计划。

## 8. 当前架构讨论的下一个主线议题

当前的 L1「服务职责与边界」已基本形成候选基线。**下一个主线议题是“服务通信与调用拓扑”**：

- Desktop Frontend / Tauri Commands / Rust Facade 的调用关系；
- Agent Service 是否直接调用 Python Worker；
- 本地 IPC/RPC、进程生命周期和超时失败策略的总体边界；
- Core 的唯一数据库写入权如何通过服务契约保持。

本 Backlog 不改变该主线，不自动提升任何延后功能的优先级。
