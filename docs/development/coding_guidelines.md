## 1. 任务启动与阅读范围

1. 先读 [项目 README](../../README.md) 和 [docs 导航](../README.md)，再定位任务相关的设计、接口、数据、配置、测试及已知问题。
2. 检查 Git 工作区、当前分支、相关代码、测试和实际契约。保护用户已有未提交修改；不得擅自覆盖、清空工作区或执行破坏性 Git 操作。
3. 明确当前任务目标、范围、输入输出、依赖、验收方式；遵循 [L3 实施顺序](implementation_spec_and_tasks.md)。不得跳过阻塞性验证；P00/P01 优先于依赖未固化契约的业务实现。
4. 如果发现关键需求不清晰、文档与实现冲突或接口不完整，先核对证据、记录影响和建议，取得必要确认；普通不影响设计的实现细节可自行处理。不要为普通任务加载无关的全部文档。

## 2. 设计边界与变更管理

- 不擅自改变已确认的需求范围、技术栈、通信协议、数据库、进程边界或人工确认规则，不为形式完整新增框架、服务、抽象层或依赖。
- Rust Core 维护权威状态、资源准入及正式文件提交；Agent Service 与 Python Worker 遵循已有接口和权限，只提供规划、计算、执行事实或候选。详细边界以 [L1](../architecture/dataset_doctor_L1_architecture_final_v1.0.md) 和 L2 各专题为准。
- 修改共享契约前识别全部调用方、生成类型、兼容性、持久化迁移和测试影响。多 Agent 不并行独立改写同一共享契约，先确定变更负责人。
- 重大架构、需求、破坏性兼容性变更、危险操作或主分支合并须由项目负责人明确授权。普通实现不得以改架构规避问题。
- 优先复用项目已有实现。新增第三方依赖记录用途、锁定版本、适用平台、许可及验证结果；真实用户数据和凭据不得进入 Git、公开日志或未经授权的外部服务。

## 3. 实现与验证

新模块采用测试驱动开发。先为具体模块和功能编写自动化验收用例，运行并确认测试能捕获缺失行为，再实现功能并复跑。用例使用独立、可重复的输入和确定的断言，提供按模块复跑的入口。按本次改动的实际影响选择当前功能、直接依赖和必要回归，已通过且未受影响模块沿用既有验收证据。共享契约、跨模块行为或实际故障涉及更大范围时，针对具体风险扩展验证。记录测试选择依据、实际结果和阻断项。涉及持久化、取消、重试、并发和恢复时覆盖对应失败场景。

单个测试场景和冒烟场景的运行预算不超过 30 秒；编译、依赖与环境准备单独计时。超过预算应拆分为独立可复用场景，保留原断言，不跳过或放宽限时。实际入口、进程树回收和耗时证据见 [测试时间预算](../testing/test_time_budget.md)。未复验的历史场景不标为已满足新预算。

使用合成、授权或可追溯的测试数据；不要把生产媒体和真实 API Key 写入测试。脚本、测试、配置与契约尚未实际存在时不得编造执行命令或测试结果。Rig 独立 PoC 已验证的范围以 [测试报告](../testing/rig_sdk_validation.md) 为准，不代替真实模型、业务集成和跨平台发行验收。

每次完成任务时汇报：修改范围、关联设计、实际执行的命令与测试结果、失败或未执行项及原因、设计偏差、文档更新和未解决问题。使用 Confirmed / Design Default / Proposed / Validated / Implemented 等状态时明确区分用户确认、设计建议、真实验证和实现；编译通过不等于功能通过。

## 4. 工程知识的唯一维护位置

| 内容 | 权威位置 |
|---|---|
| 本项目开发守则 | 本文件 |
| 需求、模块、接口、数据、配置与设计意图 | [docs 对应分类](../README.md) |
| 实际 API、Schema、迁移、运行配置 | 项目对应契约或代码文件（按 L3 创建后维护） |
| 故障、根因、解决方案、规避和预防措施 | [docs/troubleshooting/](../troubleshooting/README.md) |
| 影响架构或兼容性的技术决策 | [docs/decisions/](../decisions/adr-001-rig-agent-sdk.md)；按事项新增 ADR |
| 自动化回归与测试样例 | tests/；按需组织 testdata/ 或 fixtures |
| 可执行诊断、构建与维护工具 | scripts/（按需创建，不预先创建空目录） |
| 普通代码修改、开发流水 | Git commit / PR，不另建重复知识库 |

新增脚本按职责与平台组织，测试按类型和场景拆分。已有稳定入口保持兼容。可复用测试样本归 `testdata/`，构建产物、临时样本和验收日志归 Git 忽略的输出目录。

更新文档时引用唯一权威来源，不平行复制字段、Schema 或整份测试日志。对于已解决且有长期价值的问题，记录可复现环境、原因、修复、验证证据及预防办法；若经验形成长期约束，将规范归到对应设计/工作守则，并用链接关联问题记录。详细记录模板见 [troubleshooting 导航](../troubleshooting/README.md)。

## 5. Skill 使用与提炼原则

- 可使用开发者已安装的通用 Codex Skills 或其他工具能力；它们不能替代项目需求、接口、工作守则与实际验证，也不得突破项目权限。团队无需安装同一套个人 Skills 才能阅读、构建和维护本仓库。
- 当前不创建项目级 .agents/skills/，不把普通工程说明、代码命名、问题记录或测试要求包装成重复的 Skill。
- 优先记录问题，再按实际需求提炼长期规范、可执行诊断脚本和自动化回归测试。仅在重复出现、流程稳定、现有通用 Skill 无法覆盖、且复用收益明确时考虑项目级 Skill。
- 新 Skill 若确有必要，应说明触发条件、输入、步骤、权限、失败行为、验证方式及依赖；引用 docs 中的权威知识和现有 scripts/tests，不复制内容，也不引入平行的项目工作守则。
- 此处的开发工具 Skills 与 Dataset Doctor 产品内部的 Rig Agent/Tool/Workflow 是不同系统；不混用运行时、权限或目录。

## 6. 维护原则

随项目演进按需要修订本文件。若新规则已存在于更合适的专题契约中，在这里链接而不是复制；根目录 AGENTS.md 保持简短。保持轻量、可检索、工具无关，优先通过测试和可执行工具防止同类问题复发。
